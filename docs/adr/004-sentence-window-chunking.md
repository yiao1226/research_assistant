# ADR-004: 句子窗口分块策略

**状态**: 已采纳  
**日期**: 2025-06  
**决策者**: @yiyao1226

---

## Context（背景）

RAG 系统的分块策略直接影响检索精度和 LLM 回答质量。
常见选择有：

1. **固定大小分块**（Fixed-size chunking）: 每 512 token 切一块，重叠 50 token
2. **段落分块**：按换行/标题切分
3. **句子分块**：按句号/问号切分

科研论文的特殊性：
- 中文学位论文句子短（平均 24 tokens），英文期刊句子长（平均 70 tokens）
- 答案往往藏在一句话里（"最佳沉积温度为 850°C"）
- 但理解这句话需要上下文（前文在说什么方法，后文在讨论什么条件）

### 核心矛盾

**检索精度 vs 上下文充分性**：
- 大块（段落级）→ 上下文充分，但检索精度低（向量被无关内容稀释）
- 小块（句子级）→ 检索精度高，但上下文不足（LLM 看到孤立的半句话）

TextbooksAreAllYouNeed（2024）提出了**句子窗口检索**作为解决方案：
索引时用小粒度（句子），但检索后展开成大窗口给 LLM。

## Decision（决策）

采用**句子窗口分块 + 自适应窗口大小**：

```
索引阶段:
  论文全文 → 按标点切分为单句
  每个句子独立 encode → 存入 Qdrant
  同时存储: window_text（前后各 N 句的拼接）

检索阶段:
  query → Dense 搜索 → 命中 top-K 句子
  → post_process_sentence_window() 将 text 替换为 window_text
  → LLM 看到的是宽窗口上下文，而非孤立的命中句

窗口大小:
  中文论文: window_size=5（前后各 5 句，~250 tokens）
  英文论文: window_size=2（前后各 2 句，~350 tokens）
  自动检测: 前 5000 字中 CJK 字符 > ASCII → 中文模式
```

### Chunk 数据结构

```python
{
  "id": "uuid5(paper_id, sentence_index)",
  "text": "最佳沉积温度为 850°C。",           # 检索用（单句）
  "payload": {
    "paper_id": 42,
    "heading_path": "第三章 > 3.2 温度参数优化",
    "window_text": "基片温度是 MPCVD 工艺中... [前5句] "
                   "最佳沉积温度为 850°C。 "
                   "在此温度下，拉曼半峰宽... [后5句]",
    "chunk_index": 15,
    "chunk_count": 234,
    "char_start": 12345,
    "char_end": 12379,
    "_is_window": True       # 标记：text 已被替换为 window_text
  }
}
```

### 为什么不是段落分块

段落分块的问题是**向量稀释**：
```python
# 段落: 200 字，包含 3 个不同主题
"MPCVD 系统采用 2.45GHz 微波源。基片为硅(100)晶面。
沉积前用金刚石粉研磨 30 分钟。反应气体为 CH4/H2 混合..."
# 这 200 字的向量是什么？是 "MPCVD" 还是 "硅基片" 还是 "研磨" 还是 "气体"？
# 句子分块让每个概念有独立的向量表示
```

### 为什么不用 Semantic Chunking（LlamaIndex 默认）

LlamaIndex 的 SemanticChunker 用 LLM 或 embedding 检测语义边界再切分：
- Pro: 切分更"自然"
- Con: 需要额外的 LLM 调用或 embedding 比较 → 入库时间翻倍
- Con: 中文学术文本的语义边界检测不成熟（基于英文训练的模型可能误判）

对于单人的离线处理场景，词法切分（按标点）的性价比远高于语义切分。

## Consequences（后果）

### 正面
- 检索精度高：向量对应具体的单个概念/数据点
- 上下文充分：LLM 看到的是完整的论证链条
- 章节定位：heading_path 让 LLM 知道这段信息来自论文的哪个部分
- 无额外 LLM 调用：全部在线性时间内完成

### 负面
- 存储膨胀：每句话存两份（text + window_text），Qdrant 存储约为简单分块的 2 倍
- BGE 编码量增加：句子比段落多 5-10 倍数量 → 入库时间增加
  - 实测：一篇 200 页的学位论文 ~800 句，编码约 8 秒（BGE 在 CPU 上）
- PDF 提取质量影响切分：如果 PDF 提取的文本标点混乱，切分质量下降

### 风险
- 英文论文的句子切分依赖 `.` —— 但 "et al."、"Fig. 1"、"e.g." 会被误判为句号
  当前用简单的 `re.split(r'(?<=[。！？.!?])\s*')` 解决中英文混合场景，
  但英文缩写的误判仍然存在

## Alternatives Considered

### A. 固定 512-token 重叠块
- **否决原因**：向量被无关内容稀释，精确度远不如句子窗口

### B. 层级索引（小句 → 段落 → 章节）
- **想用但暂时没做**：先用当前方案的 heading_path 近似了这个效果
- 未来可考虑：在 Qdrant 中建 parent-child 关系（小句的 payload 里存章节 ID）

### C. LlamaIndex SemanticChunker
- **否决原因**：额外 LLM 调用的成本不适合单人项目，且中文支持未验证

---

## 面试要点

- **核心概念**：索引精度和上下文充分性是 trade-off，句子窗口是两全方案
- **关键数字**：中文 window=5 (~250t)，英文 window=2 (~350t)
- **技术细节**：post_process_sentence_window 的替换逻辑
- **为什么不是固定大小**：向量稀释 → 检索精度下降
- **为什么不是语义分块**：额外的 LLM 调用 → 入库时间翻倍
